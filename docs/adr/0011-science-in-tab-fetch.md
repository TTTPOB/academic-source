# ADR 0011：Science 的主 PDF 全程在浏览器标签页里取得

- 状态：Accepted
- 实施情况：已实现。

## 背景

Science 的 PDF 地址带签名，要先读阅读器页面才能得到。原实现有两条路：

- 从 Python 用浏览器留下的 Cookie 直接请求阅读器页面；
- 在浏览器里导航到阅读器页面，等待后从页面里取地址。

第一条路在线上几乎不成功。用同一组 Cookie 和 User-Agent 从 Python 请求，即使 Cookie 只有 3 毫秒旧，仍然得到 403 验证页；同一时刻 Chrome 请求同一地址约 0.9 秒返回 200。历史上它成功过 7 次，都紧跟在一次浏览器成功之后，成功的条件没有查明。

第二条路能成功，但每篇约 12 秒，其中包含固定的 3 秒等待和轮询。

## 决策

1. 在已登录的标签页里用同源 `fetch` 读取阅读器页面，解析出带签名的 PDF 地址，再在同一标签页里把 PDF 流式取回。
2. 这一步失败时回退到导航阅读器页面的原流程。
3. 删除从 Python 直接请求的路径，以及它使用的 Cookie 快照文件和 `science_http_proxy` 配置。
4. 删除 `ScienceCamofox` 来源。它是注册表里的一个名字，对应的代码路径在当前配置下不可达。Science 的来源链是 `ScienceBrowser`、`Crossref`、`Unpaywall`。
5. 标签页向 Python 传输文件内容时使用 base64 分块，替换原来的 JSON 数字数组。

## 理由与替代方案

- 保留 Python 直连作为最先尝试的一步：它失败时白白多花一次请求，成功的条件又不清楚，无法据此判断何时值得尝试。
- 用浏览器的下载功能把文件直接写到共享目录：传输不经过 CDP，速度更好，但要求浏览器和服务共享文件系统。线上的 Chrome 在容器里，暂不引入这一约束。
- base64 分块在本机基准里，1 MiB 文件从 5.16 秒降到 0.15 秒，20 MiB 文件 2.19 秒。

## 后果

- Science 的主 PDF 不再有无浏览器的获取路径；浏览器不可用时只剩 `Crossref` 和 `Unpaywall`。
- 已有部署里的 `science_http_proxy` 设置和 `science_http_state.json` 文件不再被读取，可以删除。

## 验证要点

- 页内读取成功时结果的来源标记为 `Science(Fetch)`，回退成功时为 `Science(Browser)`。
- 日志和结果里不出现带签名的 PDF 地址。
