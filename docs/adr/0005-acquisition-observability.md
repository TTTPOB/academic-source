# ADR 0005：逐来源诊断留在日志和任务记录里

- 状态：Accepted。其中 `candidates` 字段的方案待确认。
- 实施情况：已实现（提交 `906a83e`），单元测试覆盖。生产验收结果见完成报告。

## 背景

一次线上排查发现，`10.1126/science.aad8559` 用 `oa_first` 花了 74 秒，其中 62 秒耗在 OA 来源上，但当时没有任何记录能直接说明这一点：

- 来源尝试（`Attempt`）不记录耗时，也不写日志；
- 任务只有提交时间和更新时间，排队时间和执行时间分不开；
- 任务排队或执行时，响应里看不出它排在第几、做到哪一篇；
- OA 元数据查询成功时状态为 `discovered`，容易被读成“找到了 PDF 线索”，实际只表示服务返回了这篇文献的记录。

对外响应此前已经约定不返回逐来源的 `attempts`，只返回每篇的汇总结果（见 README）。

## 决策

1. **对外响应增加汇总层面的时间和进度**：任务的 `started_at`；每篇结果的 `elapsed_seconds`（不含排队）；排队时的 `queue.ahead`；执行时的 `progress`（第几篇、共几篇、当前标识符）。
2. **逐来源耗时不进对外响应**。每次尝试的耗时写入 `Attempt.seconds`，保存在内部任务记录里，同时写一行 INFO 日志，内容为标识符、来源、结果、原因、候选数和耗时。日志不含 `message`，因为它可能引用下载地址。
3. **`discovered` 的值不变，另加 `Attempt.candidates`**，表示这次查询得到几个候选地址。0 表示服务有这篇的记录但没有给出开放版本。**待确认**：另一种做法是把 `discovered` 改名，用户尚未在两者之间确认。
4. **旧任务记录**没有这些字段，读取时为空，对外响应省略空值。

## 理由与替代方案

- 在响应里加一个精简的逐来源列表，可以省去查日志这一步。没有采用，因为它会重新打开已经收紧的响应契约，而需要这份信息的是排查问题的运维者，他们能看日志。
- 把 `discovered` 改名更直白，但已保存的任务记录和现有客户端都使用原值。
- 执行中的任务没有给出“当前正在试哪个来源”。这需要来源层向任务层回报进度，要改 `Source` 协议，留给后续工作。

## 后果

查某个来源慢不慢，需要能访问服务日志或 SQLite 任务记录。`serve` 命令因此把 `academic_source` 日志器设为 INFO，日志量随尝试次数增加，每次尝试一行。

## 验证要点

- 对外响应不含 `attempts`；`elapsed_seconds` 不含排队时间。
- 排队任务的 `queue.ahead` 把正在执行的任务计算在内，且不写入任务记录。
- 每次尝试恰好一行日志，日志里没有下载地址。
- 没有新字段的历史记录能正常读取和投影。
