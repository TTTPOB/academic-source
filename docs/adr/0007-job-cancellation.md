# ADR 0007：取消任务时做完当前这篇再停

- 状态：Accepted
- 实施情况：已实现（提交 `d4e7ec5`），单元测试覆盖。生产验收结果见完成报告。

## 背景

任务一旦提交就只能等它跑完。命令行客户端被终止时，服务端的任务仍在继续，占着唯一的工作线程；提交错了一大批文献，也没有办法撤回。

一次来源尝试可能正在操作浏览器。浏览器会话由工作线程持有，中途打断会留下没关的标签页和写了一半的会话文件。

## 决策

1. **新增任务状态 `cancelled`**，是终态。
2. **排队中的任务立即取消**，直接写入 `cancelled`，不再计入其他任务的排队位置。
3. **执行中的任务做完当前这一篇再停。** 不开始下一篇，任务结束时写入 `cancelled`。已完成的结果和文件全部保留，没轮到的论文不产生结果。
4. **取消请求立刻返回**，不等当前这篇做完。调用方继续轮询，直到状态变为 `cancelled`。
5. **对已结束的任务取消没有效果**，返回它现在的状态。任务不存在时 HTTP 返回 404。
6. 接口：HTTP `POST /api/v1/jobs/{job_id}/cancel`、MCP `cancel_job(job_id)`，返回值与查询任务相同。

## 理由与替代方案

- 立即打断正在进行的来源尝试：能更快停下，但要强行结束线程或关闭浏览器会话，正常的清理、结果保存和文件登记都会被跳过。一篇论文通常在一分钟内结束，等它做完的代价很小。
- 复用已有的 `interrupted` 状态：它表示“服务重启时任务没做完”，是意外。取消是用户主动要求的，两者混在一起就分不清了。

## 后果

- 取消一个正在执行的任务，最长要等一篇论文的时间才真正停下。
- 取消请求只记在内存里。服务在这期间重启时，任务按原有规则标为 `interrupted`。
- 读取任务状态的客户端需要认识 `cancelled` 这个新值。

## 验证要点

- 排队中取消：状态立即变化，后面任务的排队位置随之更新，等待这个任务的调用方被唤醒。
- 执行中取消：当前这篇的结果和文件保留，其余论文没有被尝试。
- 取消后的返回值与查询任务一致；重启后 `cancelled` 记录仍可读取。
