# ADR 0002：Provider 归属与重写规则

- 状态：Accepted
- 实施情况：注册表已实现（提交 `8a11412`）。重构前后各策略的来源顺序用 253 个固定用例对照，另对 172,032 个 DOI 前缀、策略和配置的组合做过一次性对比，全部一致。目前自有的只有 OA 快路径，其余来源都是借用。

## 背景

来源（provider）的实现大多在 fork 来的 `scansci_pdf` 里，质量参差：`_publisher_strategies_core.py` 一个文件 3298 行，失败原因通过模块级变量传递。重构之前，哪些来源参与、按什么顺序，是 `_plan()` 里一段手写的列表拼接，启用条件散在其中。一个来源用不用浏览器，只能读它的实现才知道。

全部重写这些来源风险太大：每个出版商站点的行为都是实测调出来的，重写一个就可能弄坏一个。

## 决策

1. **每个来源有明确的归属。**
   - 自有：实现在 `academic_source/sources/` 下，直接返回[来源契约](0003-closed-source-errors.md)规定的类型。
   - 借用：继续调用 `scansci_pdf` 里的函数，经适配器接入。
2. **借用的来源不改行为。** 某个来源需要实质修改时，在 `academic_source/sources/` 下按契约重写，切换注册表里的引用，再删掉旧函数。不为了整洁去重写不需要动的来源。
3. **所有来源登记在一张注册表里**（`sources.registry.PROVIDERS`），字段为标签、类别、归属、后端、站点键、启用条件。各策略的来源顺序由这张表生成。
4. **后端字段默认 `browser`。** 只有逐函数核对过、确认只经 `network.fetch` 发请求的来源才标 `http`。核对结果见 [HTTP 来源核对清单](../HTTP_SOURCE_AUDIT.md)。
5. **出版商来源的 DOI 匹配和内部顺序仍由 `scansci_pdf.sources.publishers` 的出版商表决定**，注册表不复制这份规则。

## 理由与替代方案

- 一次性重写全部来源：回归风险集中爆发，而且大部分来源目前没有问题。
- 直接在 `scansci_pdf` 里修改：改动会和上游风格的代码混在一起，那个包也不受 ruff 和 pyrefly 检查。
- 把出版商的 DOI 规则也搬进注册表：会出现两份规则，而这次重构的目标之一是不改变任何来源顺序。以后迁移出版商路由时再做，用固定顺序的测试约束。

## 后果

两种归属会长期并存。读代码时不能从标签或函数名推断后端，要查注册表。后端和站点键目前只是记录，不影响执行，要等 [ADR 0004](0004-paper-level-scheduling.md) 实现后才被使用。

## 验证要点

- `tests/academic_source/test_source_plan.py` 固定了六种策略在不同出版商和配置下的来源顺序，改注册表后必须通过。
- 把一个来源从借用改为自有时：新实现符合来源契约，受影响站点有回归测试，旧函数已删除。
- 把一个来源的后端从 `browser` 改为 `http` 时：先更新核对清单。
