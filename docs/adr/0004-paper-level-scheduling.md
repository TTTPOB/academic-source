# ADR 0004：以论文为单位并行调度

- 状态：Proposed
- 实施情况：未实现。完整设计见[论文并行调度设计](../PARALLEL_SCHEDULING.md)，用户审阅后再实现。

## 背景

服务只有一个工作线程，所有论文排成一列处理。一个慢来源会拖住同一任务的其余论文和其他所有任务。

并行受两个条件限制。浏览器对象只能在创建它的线程上使用。借用的出版商代码把失败原因放在一个模块级变量里，整个进程只有一份，多个线程同时跑浏览器来源时会互相覆盖。

## 决策

1. **并行的单位是论文。** N 个论文线程各处理一篇。一篇论文内部仍按策略顺序逐个试来源，第一个成功就停。
2. **浏览器只有一个线程。** 注册表里后端为 `http` 的来源在论文线程上直接执行；后端为 `browser` 的来源交给浏览器线程，论文线程等待结果。OA 快路径里用 CDP 重试被拦截候选的那一步也交给浏览器线程。
3. **同一站点的并发由 `upstream_client` 的 HTTP 闸门限制。** 不同站点之间并行，同一站点内部排队。`host_concurrency` 可以按站点覆盖上限。
4. **默认 N=1**，行为与现在相同。配置键为 `settings.json` 顶层的 `paper_workers`。

**待确认：**

- 没有单独配置的站点，默认并发上限建议为 1。这来自反爬的一般经验，没有在本项目实测过。
- N>1 时是否强制要求禁用 Sci-Hub。Sci-Hub 来源内部有自己的线程池，会在别的线程上创建浏览器，不受第 2 条约束。

## 理由与替代方案

- 在一篇论文内部并行试多个来源：会改变“按顺序、第一个成功就停”的语义，也会向本来不必访问的站点发请求。
- 每个论文线程各用一个浏览器：线上用的是一个外部 Chrome 的 CDP 连接，登录状态和 Cookie 都在那一个浏览器里；模块级的错误变量也不允许多个线程同时跑浏览器来源。

## 后果

- 论文线程等浏览器时被占住。浏览器来源多的批量任务，并行收益有限。
- 现在每个任务结束时都关闭浏览器。并行后浏览器会话要跨任务保留，只在应用关闭时关一次。
- 任务进度现在是整条记录覆盖写入，并行后必须由调度者一方负责保存。
- HTTP 闸门管不到浏览器发出的流量，因此不能保证一个站点收到的总请求数。
