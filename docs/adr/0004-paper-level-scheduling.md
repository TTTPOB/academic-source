# ADR 0004：以论文为单位并行调度

- 状态：Accepted
- 实施情况：已实现。规则、配置和限制见[论文并行调度](../PARALLEL_SCHEDULING.md)。

## 背景

服务原先只有一个工作线程，所有论文排成一列处理。线上任务的总耗时中位数 141 秒、九成位 714 秒，大部分时间花在排队上。

并行受两个条件限制。出版商会对同一来源的密集请求触发验证或封禁。借用的出版商代码把浏览器对象和失败原因放在模块级变量里，整个进程只有一份。

## 决策

1. **并行的单位是论文。** `paper_workers` 个论文线程各处理一篇。一篇论文内部仍按策略顺序逐个试来源，第一个成功就停。
2. **同一站点默认同时只有一个请求**，`source_config.host_concurrency` 可以按站点覆盖。不同站点之间并行。
3. **浏览器按站点并行。** 最多 `browser_tabs` 个浏览器线程（默认 10），每个线程持有自己的 Playwright 实例和 CDP 连接，连到同一个 Chrome。浏览器对象和失败原因改为线程局部变量。
4. **来源按是否真的驱动浏览器分类**，注册表记录 `browser`、`http`、`http_ungated` 三种后端。只有 `browser` 来源进入浏览器线程。
5. **机构登录类来源串行**，共用一把锁。
6. **`paper_workers` 大于 1 时要求禁用 Sci-Hub**，否则拒绝启动。Sci-Hub 来源自带线程池和浏览器，调度器约束不了。
7. **默认 `paper_workers=1`**，走原来的串行路径。

## 理由与替代方案

- 在一篇论文内部并行试多个来源：会改变“按顺序、第一个成功就停”的语义，也会向本来不必访问的站点发请求。
- 所有浏览器操作共用一个线程：实现最简单，但浏览器来源是最慢的一类（单次 10 秒以上），串行后并行收益所剩无几。同一个 Chrome 可以同时驱动多个标签页，按站点限制已经足以避免对单个出版商并发。
- 每站点默认并发取 1：没有各出版商承受能力的实测数据，先取最保守的值。

## 后果

- 论文线程等站点名额或浏览器线程时被占住。集中在同一站点的批量任务，并行度接近 1。
- 并行模式下浏览器会话跨任务保留，只在服务关闭时关一次。
- 任务记录由调度器一方写入；进度指向正在处理的论文里序号最小的一篇。
- 站点限制不覆盖浏览器内部的子请求，也不把同一站点的 HTTP 请求和浏览器请求合并计数。

## 验证要点

- 不同站点的两篇论文同时执行，同一站点的两篇排队，`host_concurrency` 覆盖生效。
- 两篇论文同时使用浏览器时，各自的失败原因不串，一方结束不关闭另一方的标签页。
- 一批论文乱序完成后，结果顺序、完成计数和任务记录正确。
- `paper_workers=1` 时原有测试全部通过。
