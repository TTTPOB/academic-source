# 论文并行调度设计

本文是设计提案，尚未实现，对应 [ADR 0004](adr/0004-paper-level-scheduling.md)。各来源能否离开浏览器线程的逐函数依据见 [HTTP 来源核对清单](HTTP_SOURCE_AUDIT.md)。

## 要解决的问题

服务现在只有一个工作线程，所有论文排成一列。一篇论文卡在慢来源上时，同一任务的其他论文和其他任务都在等。

## 模型

- **并行的单位是论文。** N 个论文线程各取一篇处理。一篇论文内部不变：按策略顺序逐个试来源，第一个拿到可读 PDF 的来源胜出，后面的不再试。
- **浏览器只有一个线程。** 论文线程走到需要浏览器的来源时，把这一次尝试交给浏览器线程，自己等结果。
- **同一站点的并发由 HTTP 闸门限制。** 不同站点之间并行，同一站点内部排队。

默认 N=1，行为与现在完全相同。

```text
任务 A: 论文1 论文2      论文线程 1 ─┬─ http 来源：本线程直接执行
任务 B: 论文3       →    论文线程 2 ─┤
                         ...        └─ browser 来源：交给浏览器线程，等待结果
                                                         │
                                                  浏览器线程（唯一）
```

## 1. 哪些来源可以在论文线程执行

注册表给每个来源标 `http` 或 `browser`。只有逐函数核对过、确认全部请求都经过 `network.fetch` 且没有浏览器分支的来源才标 `http`：

> Unpaywall、OpenAlexOA、OpenAlexContent、EuropePMC、CORE、PMC、Crossref、NatureDirect、arXiv，以及 OA 快路径的元数据查询和 HTTP 候选下载。SciBban 是空实现，也归入 `http`。

其余一律标 `browser`，分三种情况：

| 情况 | 例子 | 为什么不能标 `http` |
|---|---|---|
| 会打开浏览器 | 各 `*Browser` 来源、ScienceDirect、CopernicusDirect、LibGen、Sci-Hub、CARSI、WebVPN、EZProxy | 浏览器对象只能在创建它的线程上使用 |
| 不开浏览器，但用自己的 `requests.Session` | OpenAIRE、DOAJ、CrossrefPage、PublisherDirect、MDPIDirect、PNASDirect、PLOSDirect、FrontiersDirect、BMCDirect、SpringerTDM、ElsevierAPI、SAGECN | 请求不经过 HTTP 闸门，并行后同一站点的并发不受控。ElsevierAPI 还会写共享的 Cookie 文件 |
| 交给进程外的执行器 | SessionBroker | 无法从本项目代码确认它不用浏览器 |

第二类来源改为经 `network.fetch` 发请求并重新核对后，可以逐个改标 `http`。不能凭函数名判断：`try_science_direct` 名字里没有 Browser，内部却会调远端浏览器。

**交接的粒度是一次完整的来源尝试。** 旧出版商代码把失败原因放在模块级全局变量里（`_publisher_strategies_core.get_last_error()`）。“清空错误 → 调用来源 → 读取错误”这三步必须在浏览器线程的同一次回调里完成，否则会读到下一次尝试的错误。

### HTTP 闸门需要的改动

`upstream_client` 目前只给 OpenAlex、Crossref、arXiv 配了限速和并发上限，其他域名不限。并行之前需要做三件事：

1. **没有配置的站点给一个默认并发上限，建议 1（待确认）。** 这个值来自反爬的一般经验，没有在本项目实测过。`source_config.host_concurrency` 可以按站点覆盖。
2. **重定向后的目标站点也要过闸门。** 现在只在初始 URL 上准入一次，跳转到出版商 CDN 之后不再计数。应改为每一跳单独准入：先关闭上一跳的响应并归还名额，再申请下一跳。
3. **`requests.Session` 按线程分开。** 现在同一个代理配置下所有线程共用一个 Session，而 Session 不是线程安全的。

浏览器发出的流量和第二类来源的流量不经过闸门，所以闸门不能保证一个站点收到的总请求数。

## 2. OA 快路径如何使用浏览器

OA 快路径（`acquire_oa`）大部分是 HTTP：查元数据、下载候选。只有最后一步例外：配置了 CDP 时，对最多两个被拦截的候选用浏览器重试（`_browser_candidate`）。

做法是给 `acquire_oa` 传入一个“在浏览器线程上执行”的函数，只把 `_browser_candidate` 这一步交过去，其余留在论文线程：

1. 论文线程查元数据、下载候选，命中即返回，不碰浏览器。
2. 全部未命中时，把第一个被拦截的候选交给浏览器线程，等结果；失败再交第二个。不同时提交两个。
3. 标签页的创建、导航、读取、关闭都在这一次回调里完成。回传的只有下载结果和诊断信息，不传页面对象。

尝试耗时从浏览器线程开始执行时算起，在浏览器队列里等待的时间单独记录。

## 3. 浏览器何时关闭

现在 `Application._run` 在每个任务结束时调用 `source.close()` 关闭浏览器。并行后，一个任务结束时别的任务可能正在用浏览器，这个时机不再成立。

- N>1 时，浏览器会话跨任务保留，只在应用关闭时关一次。每次回调负责关掉自己开的标签页。
- `source.prepare()`、所有浏览器访问、`source.close()` 都在浏览器线程上执行。
- 应用关闭的顺序：停止接收新任务 → 等已接收的论文做完（此时浏览器线程照常工作）→ 在浏览器线程上 `source.close()` → 停掉浏览器线程 → 释放数据目录锁。
- CDP 后端的 `close` 只关闭本应用创建的标签页并断开连接，不会结束外部的 Chrome。

有两处不属于“来源”但也会用浏览器，需要走同一个浏览器线程：

- **补充材料下载**（`fetch_supplementary`）在 HTTP 失败时会回退到浏览器。整次调用交给浏览器线程。
- **Sci-Hub** 内部有自己的线程池，会在别的线程上创建浏览器，外层无法约束。建议 N>1 时要求 `scihub_enabled=false`，否则拒绝启动（待确认）。线上环境本来就禁用了 Sci-Hub。

## 4. 下载地址去重的状态

`config["_acquisition_attempted_urls"]` 是一个集合，记录这篇论文已经试过的下载地址，避免快路径和后续来源重复下载同一个地址。它放在配置字典里，但其实是运行时状态。

核对结果：`LegacySources.acquire` 每次调用都新建这个集合，`Application._acquire` 传入的也是配置的深拷贝，所以它不跨论文共享。并行后保持这一点即可。同一篇论文同一时刻只有一个来源在执行，集合不需要加锁。

## 5. SQLite 与任务进度

`Store` 每次操作新开一个 SQLite 连接，写事务很短，SQLite 自己会让并发的写排队（等待上限 10 秒）。数据库层面不需要加锁，也不必先改 WAL 模式。

真正的问题在上一层：`save_job` 每次把整个任务序列化后覆盖写入。两个论文线程如果各自持有一份任务对象并分别保存，后写的会抹掉先写的结果。

- 任务对象只由调度者一方持有和保存。论文线程只返回“第几篇、结果是什么”。
- 结果按输入顺序存放，与完成的先后无关。全部收齐后才写终态。
- 分配论文时在任务之间轮转，不把一个大任务的所有论文一次性排进队列，否则后提交的小任务仍然要等大任务做完。
- `progress.identifier` 现在是单个值。并行后取正在执行的论文里序号最小的一篇。`queue.ahead` 改为从调度队列计算。
- 两个线程同时获取同一篇未缓存的论文时，会各下载一次，后写的缓存记录覆盖先写的。首版接受这种重复。

## 6. 配置

| 项 | 值 |
|---|---|
| 配置键 | `settings.json` 顶层的 `paper_workers` |
| 取值 | 正整数 |
| 默认 | 1 |
| 试运行建议 | 2 |

`paper_workers` 不属于 `source_config`，不影响结果缓存键。旧的 `job_workers` 维持现状：值为 1 时忽略，其他值报错，错误信息提示改用 `paper_workers`。

`paper_workers=1` 走现有代码路径。大于 1 才启用论文线程池、独立的浏览器线程和站点默认并发上限。回退只需改回 1 并重启，任务数据不用动。

## 实现后的验收

1. 两篇不同站点的论文确实同时在执行；同一站点的两篇排队；`host_concurrency` 覆盖生效；流式下载失败后名额被归还。
2. 两篇论文先后使用浏览器时，在同一个线程上执行，错误原因不串；OA 快路径 HTTP 命中时不向浏览器线程提交任务；一个任务结束不影响另一个任务的标签页。
3. 同一地址在一篇论文内只下载一次，在另一篇论文里仍可下载；一批论文乱序完成后，结果顺序、完成计数和任务记录都正确。
4. `paper_workers=1` 时现有全部测试通过。
